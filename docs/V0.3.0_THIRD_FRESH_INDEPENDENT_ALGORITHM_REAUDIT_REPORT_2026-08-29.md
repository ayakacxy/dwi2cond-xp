## 结论

本轮结论是：**v0.3.0 的标准主流程已经基本复现了 SimNIBS 4.6.0 的阶段顺序，上一轮
修复的 raw-b0、sinc、TOPUP support、FNIRT 正行列式导数、vecreg mask、post-mask 和
FEM 事务问题没有被重新打开；但仍不能表述为“与官方实现完全相同”。**

本轮确认 **2 个 P1 + 5 个 P2** 仍处于 open 状态，没有发现 P0：

| 编号 | 严重度 | 摘要 | 公开 tag 状态 |

## 2. 先审流程：官方与 v0.3.0 的端到端映射

| 阶段 | SimNIBS 4.6.0 | v0.3.0 | 本轮判定 |

| storage reorient | `fslreorient2std` 后继续使用 PE/bvec 输入 | `orientation.py` 后进入各 producer | 高层顺序一致；离散算法受 `053` 影响 |

剩余问题主要位于普通 fixture 很难触发的分支和真实 producer→consumer composition。

## 3. D2C-030-053：离散 orientation 算法仍不等于 FSL

### 3.1 实现差异

tag 的 `src/dwi2cond_xp/preprocessing/orientation.py:13-29` 使用
`nib.orientations.io_orientation()`，再按 determinant 变换到 RAS/LAS。

FSL 6.0.4 的真实链是 `fslreorient2std:104-132` → `fslhd` orientation labels →
`fslswapdim`。orientation labels 来自 NewNifti
`legacyFunctions.cc:485-596`：

1. 用 float 对三列归一化；
2. 按固定顺序执行 Gram-Schmidt；
3. 枚举 216 个有符号轴组合；
4. 只保留 handedness 相同的组合；
5. 用严格 `>` 和固定遍历顺序选择最大 trace。

NiBabel 使用 SVD/polar 判定，两者不是一般 affine 上的同一个算法。

### 3.2 本轮真实 FSL 复现

输入为有效、有限、非奇异 4D NIfTI：

```text
affine =
[[ 0.601011634,  1.401550531, 0.942415297,  92.374305725],
 [ 0.538023829, -1.309910774, 1.315203071, -25.246667862],
 [-0.660363793,  0.208347276, 1.929259419,  25.766641617],
 [ 0.000000000,  0.000000000, 0.000000000,   1.000000000]]

det(affine[:3, :3]) = -5.065160968553407
```

本轮在真实 `/usr/local/fsl/bin/fslreorient2std` 上得到：

| 实现 | NiBabel | 输出 shape | 与 FSL 数组相等 |
|---|---:|---:|---:|
| FSL 6.0.4 | — | `(3, 4, 5, 2)` | — |
| tag local | 5.3.3 | `(4, 5, 3, 2)` | false |
| tag local | 5.4.2 | `(4, 3, 5, 2)` | false |

FSL 与两个 local 结果的 affine 最大绝对差分别约为 `2.343966` 和 `2.002562`。同一个
输出 voxel-y PE 轴的单位物理方向为：

```text
FSL:       [-0.72631691,  0.67882701, -0.10797053]
local 5.4: [ 0.57652091,  0.51609981, -0.63345452]
dot = 1.6703e-08; angle = 89.999999 degrees
```

官方脚本和本地 workflow 都在 reorient 后继续消费同一个 PE 字符串。因此这不是只影响
header 展示：它可把 TOPUP/EDDY 的 PE 方向放到不同物理轴，继而传播到 warp、tensor、
PPD、conductivity 和 FEM。

### 3.3 整改要求

1. 精确实现 FSL 6.0.4/NewNifti 的 float32 归一化、Gram-Schmidt、signed-permutation
   枚举和严格 tie-breaking；
2. 保留 sform 优先、qform fallback、q/s code 和 storage handedness；
3. 增加上述 affine 的真实 FSL data/shape/qform/sform A/B；
4. 增加 producer 级 PE 物理向量断言，不得只检查 `aff2axcodes`；
5. 在 NiBabel 5.3/5.4 下必须得到同一个项目结果。

## 4. D2C-030-054：公开 tag 的 FNIRT 依赖稳定性仍未关闭

### 4.1 tag 的安装合同与验证合同不一致

tag `pyproject.toml:33-41` 声明：

```text
nibabel>=5,<6
numba>=0.64,<1
numpy>=2,<3
scipy>=1.11,<2
```

但 `constraints-simnibs46.txt` 和 `environment.yml` 的验证栈是 NumPy `2.3.0`、Numba
`0.64.0`、NiBabel `5.3.3`、SciPy `1.17.1`。tag 的
`tests/test_release_environment.py:13-27` 只检查冻结文件彼此一致，不检查 project
dependencies；CI 和 Release workflow 直接 `pip install .[...]`，没有应用 constraint。
因此普通 wheel 安装仍可解析到未经门禁验证的组合。

当前未提交工作树已把 NumPy/Numba 改为精确 pin，并添加 project metadata 回归。这是
合理的发布安全缓解，但在 commit/tag/Release 更新前，公开 `v0.3.0` 的问题状态仍为 open。

### 4.2 本轮同输入真实 FSL 复现

测试节点为
`tests/test_preprocessing_nonlinear.py::test_positive_determinant_fnirt_endpoint_matches_real_fsl`，
固定 `24×23×22` 输入、单 worker、OpenBLAS/OMP 单线程和真实 FSL FNIRT：

| 环境 | NumPy | Numba | NiBabel | corrected image relative L2 | field relative L2 | 结果 |
|---|---:|---:|---:|---:|---:|---:|
| 冻结验证栈 | 2.3.0 | 0.64.0 | 5.3.3 | `<0.005` | `<0.25` | `1 passed in 37.13s` |
| tag 允许的新组合 | 2.4.6 | 0.66.0 | 5.4.2 | `0.0061349105` | `0.3948259303` | failed |

仓库门禁是 image `<0.005`、field `<0.25`、component max `<1.2 mm`。新组合至少前两个
门禁确定失败；不是 coverage 数字、pytest 并发或无 FSL 的自洽测试。

此前的轨迹 trace 已将第一次分叉定位到底层线性代数/PCG 数值语义：极小的 inverse、
gradient、Hessian 与归约差异改变 PCG 停止点，随后改变 LM accept/reject。当前没有证据
指向新的坐标、单位、spline expansion 或 mask 公式错误，也没有 RNG 路径；但这仍说明
项目的宽依赖范围不满足固定 FSL 6.0.4 子集的稳定计算合同。

冻结栈本身也只能称为“通过现有端点门禁”，不能称为位移场逐值相同。既有冻结证据中
field relative L2 约 `0.17549`，真实 HCP PPD/conductivity/FEM A/B 仍未完成。

### 4.3 整改要求

1. 先将普通 wheel 元数据、constraint、environment 和 CI 安装合同统一到验证过的精确
   NumPy/Numba 组合；
2. 增加 wheel METADATA 回归，不能只检查 constraint 文本；
3. 增加最小/最大受支持组合的真实 FNIRT/TOPUP/PPD 门禁；
4. 不得通过放宽 image/field/max 阈值关闭问题；
5. 若未来重新放宽依赖，应先固定或显式验证 PCG/LM 的版本稳定语义。

## 5. D2C-030-055：raw QA 拟合模式未进入 cache identity

`workflow.py:843-853` 的 `run_raw_fit()` 实际将
`config.fit_compatibility_mode` 传给 `fit_dti_nifti()`，但对应
`StageDefinition` 在 `workflow.py:883-895` 的 parameters 只有 workers 和固定 fit 文本，
dependencies 为空。`pipeline.py:410-432` 的 fingerprint 只使用显式 inputs、dependencies、
parameters、implementation 和 runtime identity，不会分析 Python closure。

本轮在 tag 临时诊断副本中，把现有 cache 测试的第二次配置从 `strict-fsl` 改为 `robust`，
期望所有受影响 stage 重新运行。实际第二次状态为：

```text
fit_raw_dti_qa = cached
preprocess_nomoco = completed
register_t1 = completed
publish_tensor = completed
pipeline_qa = completed
```

这证明碰撞只发生在 raw QA stage：主 corrected fit、primary T1 transform 和正式 tensor 会
按新模式重跑，不受旧 raw tensor 污染；但 raw FA/SSE/valid/QA、raw 6DOF QA matrix、
registered raw maps 和 aggregate QA 会由新 run 消费旧模式结果。

这不是纯理论参数。`nifti_fit.py:163-170` 中 `strict-fsl` 与 `robust` 对 NaN、finite 和
positive support 的处理不同，现有 `tests/test_nifti_fit.py:186-277` 已证明输出域可不同。

整改应把 `fit_compatibility_mode` 加入 `fit_raw_dti_qa` parameters，并增加同一 output/cache
目录下 `strict-fsl → robust` 和反向切换的判别测试，明确 raw stage 和下游 QA 均重新计算。

## 6. D2C-030-056：完整 workflow 漏掉官方 CHARM sentinel

官方 `dwi2cond.t1reg.source.sh:2-20` 在任何 FLIRT/FNIRT 前检查 T1、labeling、
bias-corrected T1，并强制 `m2m_*/final_tissues.nii.gz` 存在；缺失时明确报告当前版本需要
CHARM segmentation。tag 的 standalone `register-t1` 在 `cli.py:804-818` 也检查该文件，
公开 `INPUT_CONTRACT.md` 同样将其列为必需。

完整 workflow 却在 `workflow.py:77-109` 只于 `require_fem=True` 时加入
`final_tissues`，而 `workflow.py:245-247` 仅当 `fem_smoke != "none"` 才开启该检查。
CLI 默认 `fem_smoke="none"`、publish 为 true。

所以默认 `run-pipeline`/`run-prefit-pipeline` 可在官方会于注册前拒绝的 m2m 目录上完成
T1 注册并发布正式 tensor。`final_tissues` 不直接参与 tensor 数值，故本项定 P2 而非 P1；
但这是正式入口和发布状态差异，不能忽略。

整改应让所有 T1 workflow 无条件要求 `final_tissues`，并增加
`fem_smoke=none + missing final_tissues` 的 workflow 级回归。

## 7. D2C-030-057：FEM mesh fallback 未进入真实 SESSION

tag 的 `workflow.py:80-90` 和 `simulation.py:57-74` 在标准 `<subject>.msh` 不存在时，
明确接受目录中唯一的 `*.msh`；测试也断言 `only.msh` fallback 可用。静态验证与 dry-run
因此都会通过。

但 `simulation.py:197-216` 构建 SESSION 时只设置 `session.subpath`、EEG cap 和 tensor，
没有设置已经解析的 `input_contract["head_mesh"]`。SimNIBS 4.6
`sim_struct.py:158-180` 随后执行 `SubjectFiles(None, subpath)`；
`file_finder.py:430-441` 强制目录 basename 为 `m2m_<id>`，并重新构造 `<id>.msh`。

后果是：

- `m2m_<id>` 中唯一但非标准名 mesh 会通过本地 validation/dry-run，真实 solve 前却寻找
  `<id>.msh` 并失败；
- 非 `m2m_<id>` 目录可通过部分本地 T1 workflow，但真实 SimNIBS 在解析 subject ID 时晚失败；
- 当前 fake SESSION 测试没有执行 faithful `_prepare()`，所以没有发现 producer→consumer
  组合矛盾。

整改应统一支持策略：若保留 fallback，就将 resolved mesh 显式赋给 `session.fnamehead`，
同时为需要 subject assets 的路径验证 `m2m_<nonempty-id>`；增加真实或 faithful
`SESSION._prepare()` composition 测试，并让 dry-run 也覆盖这项兼容性检查。

## 8. D2C-030-058：FEM cache 没有绑定真实 SimNIBS 计算身份

`workflow.py:276-294` 的 `_simnibs_runtime_identity()` 记录 distribution version、
`simnibs/__init__.py` 路径和该单一文件 SHA-256。FEM stage 把这份字典放入 parameters，
通用 runtime identity 还会记录 distribution 和已加载 threadpool library 版本。

问题是实际计算由 `run_simnibs`、`sim_struct.py`、`cond_utils.py`、mesh/FEM 模块及 solver
实现完成。保持 `simnibs==4.6.0` 和 `__init__.py` 不变、只替换这些实际模块或 solver 时，
FEM stage fingerprint 不变，可静默复用旧结果。现有
`tests/test_preprocessing_workflow.py:1090-1120` 只验证 init 文件 hash，正好固化了这个盲区。

本项需要同版本本地修改、重新打包或 solver 漂移才触发，故定为条件性 P2。建议将 cache
identity 绑定到安装分发的 RECORD/关键模块集合与实际 solver identity；如果不能完整确定
计算身份，应禁用 FEM cache hit，而不是用单个入口文件代表整个后端。

## 9. D2C-030-059：VN 的非零秩亏 tensor 与官方逐语句结果不同

公开 `tensor-to-mesh` 路径为 `cli.py:1287-1305` → `simnibs_adapter.py:41-84` →
`conductivity.py:tensors_to_conductivity()`。tag `conductivity.py:176-179` 计算 determinant
scale 后执行：

```text
determinant_scale[determinant_scale == 0] = 1.0
```

SimNIBS 4.6 `cond_utils.py:257-266` 只修复全零 tensor，然后直接除以
`abs(prod(eigenvalues))^(1/3)`，之后才 `_fix_eigv()`；没有上述 guard。

判别输入为一个 anisotropic tissue、VN mode、scalar conductivity `0.126 S/m`、tensor
`diag(1, 1, 0)`：

```text
local conductivity = diag(0.252, 0.252, 0.02714588)  # finite
literal SimNIBS 4.6 eigenvalue path = [NaN, NaN, NaN]
```

现有测试覆盖 SPD、全负、全零和 excentricity，但没有覆盖“非零且 rank-deficient”的 VN。
README 将所有修复笼统描述为 SimNIBS safety contract，没有声明这一分支是主动稳健化。

本项不影响完整 workflow 的正式 FEM stage：`run_tdcs` 将 tensor 交给真正 SimNIBS，未调用
本地 converter。受影响的是公开 `tensor-to-mesh` API/CLI，因此定为 P2。

整改不应简单删除 guard。应先明确产品合同：

- 若要 strict SimNIBS 4.6 等价，非零奇异 tensor 应复现官方结果或在进入计算前明确失败；
- 若要 robust 扩展，应显式提供模式、记录修复计数、加入判别测试，并停止称该分支为逐语句
  官方等价。
